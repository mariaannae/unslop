# De-AI — Framework & MVP Specification

## Version 1.1 — Framework-first implementation plan

> **Purpose of this document**
>
> This document is an implementation specification for an in-IDE coding LLM. It defines the architecture and the first implementation milestones for **De-AI**, a mobile-friendly web game in which a player edits AI-looking prose until it no longer satisfies the game's recognition criterion.
>
> The immediate goal is **not** to solve the research problem of how humans detect AI writing. The immediate goal is to build a clean, modular game framework in which different scorers, guardrails, referees, and passage sources can be swapped through configuration without changing the core game or UI.
>
> Future sophistication is deliberately described below so that the initial implementation leaves appropriate seams for it, but **future systems should not be implemented prematurely**.
>
> **Changes in v1.1:** removed the daily-passage concept entirely (passages are drawn at random from the library via a button on the game page); added an evaluation harness milestone; made meaning/fluency a v1-gameplay guardrail; specified how remote guardrails receive scorer output; added Appendix A with starting prompts and the bank-generation script.

---

# 1. Product concept

## 1.1 Core game

The player is shown a short passage that is intended to read as recognizably AI-written.

The player may edit the passage freely, including changing one word or many words.

The player presses **Check** when they want the game to evaluate the current passage.

The game evaluates the current passage and determines whether the player has won.

At any time the player may press **New passage** to discard the current puzzle and draw a fresh random passage from the library.

The intended player experience is:

1. Read an obviously AI-like passage.
2. Notice stylistic characteristics that make it feel AI-generated.
3. Rewrite it while preserving its meaning.
4. Check the result.
5. Use feedback to guide further edits.
6. Win when the passage is sufficiently human-like and still valid.
7. Press **New passage** to play again.

## 1.2 Important conceptual distinction

The game's scoring mechanism is intended to measure **perceived AI-likeness**, not to establish the actual authorship provenance of the text.

In other words:

- The game does not need to determine whether a passage was literally generated by AI.
- A passage that was generated by AI can be used as a starting puzzle.
- The relevant question for the game is whether the active scorer judges the **current text** as AI-like.

The scorer is therefore a replaceable game component, not a claim that the game has solved AI authorship detection.

---

# 2. Immediate implementation objective

Build the smallest complete framework that can support the game loop while keeping the following components independently replaceable:

- Passage source
- Scorer
- Guardrails
- Referee
- Game configuration
- LLM/API provider

The first working implementation should be able to run with:

- a static hard-coded passage bank,
- a simple mock scorer,
- one or two simple local guardrails,
- no referee,
- a configurable score threshold,
- a configurable Check budget.

Only after that framework works should a real LLM scorer be added.

## 2.1 Non-goals of the first implementation

Do NOT build these yet unless they are required to establish an interface:

- human-annotated training data
- trained AI-detection classifiers
- embeddings
- in-browser language models
- commercial AI detectors
- sophisticated semantic similarity
- automatic difficulty search
- optimal edit-path generation
- runtime passage generation
- accounts
- leaderboards
- analytics infrastructure
- social sharing
- streaks
- daily puzzles of any kind (there is no "puzzle of the day"; every passage is a random draw)
- sophisticated referee logic
- elaborate tell-card systems
- sophisticated local NLP/rule engines

The architecture should make those future features possible without requiring a rewrite.

# 3. Design principles

## 3.1 Modularity first

The core pipeline must depend only on interfaces/contracts.

It must not contain provider-specific or implementation-specific logic such as:

```text
if scorer === "claude" ...
if scorer === "openai" ...
if guardrail === "embedding" ...
```

Module selection belongs in configuration/registry code.

## 3.2 Configuration-driven experimentation

The active implementations must be selected by a single configuration object.

Example:

```ts
export const gameConfig = {
  passageSource: "static-bank",
  scorer: "mock",
  guardrails: ["not-empty", "length-ratio"],
  referee: "none",
  win: {
    scoreAtOrBelow: 2,
  },
  budget: {
    checksPerPuzzle: 6,
  },
};
```

Changing a scorer, guardrail, or referee should not require changes to core game logic or UI components.

## 3.3 Keep the first scorer simple

The first real scorer may be a single LLM call.

Do not build a custom detection model in v1.

The scorer should have a stable interface so future scorers can later include:

- other LLM judges,
- different prompt/rubric versions,
- deterministic rule-based scorers,
- commercial detectors,
- locally hosted models,
- browser-based models,
- human-calibrated classifiers,
- ensembles.

## 3.4 Keep provider access behind an adapter

The game should not know whether a scorer uses:

- Anthropic,
- OpenAI,
- another API,
- a local model,
- browser inference.

The provider layer should expose a narrow task-oriented interface.

## 3.5 Mobile-first

The final game must be playable in a phone browser.

Do not introduce heavyweight browser ML into the first release.

The editor and controls must work with touch input.

## 3.6 Build tests/framework before visual polish

The first milestones should establish:

1. types/interfaces,
2. registry/configuration,
3. pipeline,
4. mock implementations,
5. tests,
6. then API-backed implementations,
7. then an evaluation harness,
8. then UI polish.

## 3.7 Measure scorers, don't just swap them

Because scorers are replaceable, there must be one script that runs any registered scorer over the same corpus and reports the score distribution. Without it, "swapping the scorer" is a code change rather than an experiment. This is a script, not a framework feature, and it is built in Milestone 3b.

# 6. Core domain model

The core game should operate on domain objects, not provider-specific objects.

## 6.1 Evaluation context

```ts
export type EvalContext = {
  puzzleId: string;
  original: string;
  current: string;
  checksUsed: number;
};
```

This object contains enough information for a scorer/guardrail/referee to evaluate a state.

It may be extended later, but avoid placing provider-specific data here.

## 6.2 Tell

```ts
export type Tell = {
  label: string;
  quote: string;
};
```

A tell is optional explanatory feedback associated with text that a scorer considers relevant.

The framework should not assume every scorer produces tells.

## 6.3 Score result

```ts
export type ScoreResult = {
  score: number;
  tells?: Tell[];
  raw?: unknown;
};
```

For the initial scorer, `score` is an integer from 0 to 10.

Interpretation:

- 10 = strongly AI-like according to the active scorer's rubric
- 0 = strongly human-like according to the active scorer's rubric

This is a game score, not an objective probability.

Tells are optional because future scorers may not be able to provide them.

The framework must continue to work when `tells` is empty or absent.

`raw` carries the scorer's underlying payload (for example, the parsed JSON from an LLM task). Remote guardrails may read it (see §6.4 and §9). The core pipeline and UI must never depend on its shape.

## 6.4 Guardrail result

```ts
export type GuardrailResult = {
  pass: boolean;
  reason?: string;
};
```

A guardrail determines whether the current text satisfies some validity constraint.

Examples:

- non-empty text,
- acceptable length ratio,
- meaning preserved,
- fluent/grammatical,
- semantic similarity.

The framework supports both local and remote guardrails. A **remote** guardrail runs after the scorer and receives the scorer's `ScoreResult` as a second argument, so it may derive its verdict from `score.raw` (for example, `meaning_preserved` and `fluent` fields returned by the same LLM call) without making a second network request. A remote guardrail may instead make its own call; the pipeline does not care which.

## 6.5 Referee result

```ts
export type RefereeResult = {
  approved: boolean;
  reasons: string[];
};
```

A referee is an optional final adjudicator that can inspect an otherwise winning result.

The initial implementation uses a `none` referee.

## 6.6 Passage

```ts
export type Passage = {
  id: string;
  text: string;
  topic?: string;
};
```

Do not require `par` or other derived difficulty metadata in the first core type.

Those can be added later.

## 6.7 Interfaces

```ts
export interface Scorer {
  id: string;
  score(ctx: EvalContext): Promise<ScoreResult>;
}

export interface Guardrail {
  id: string;
  local: boolean;
  check(ctx: EvalContext, score?: ScoreResult): Promise<GuardrailResult>;
}

export interface Referee {
  id: string;
  verify(ctx: EvalContext, score: ScoreResult): Promise<RefereeResult>;
}

export interface PassageSource {
  id: string;
  getRandom(excludeId?: string): Promise<Passage>;
}
```

The `local` property on guardrails exists so the pipeline can distinguish no-network checks from checks that require a model/API. Local guardrails are called without a `score` argument; remote guardrails are called with one.

`PassageSource` has a single method. `excludeId` lets the caller avoid immediately repeating the passage just played. There is no date-based method.

# 7. Configuration

Create one authoritative game configuration.

Example:

```ts
export const gameConfig = {
  passageSource: "static-bank",

  scorer: "mock",

  guardrails: ["not-empty", "length-ratio"],

  referee: "none",

  win: {
    scoreAtOrBelow: 2,
  },

  budget: {
    checksPerPuzzle: 6,
  },

  guardrailParams: {
    "length-ratio": {
      min: 0.7,
      max: 1.3,
    },
  },
} as const;
```

The exact field names may change if the implementation has a good reason, but preserve the concept and use `passageSource` consistently.

The UI should not hard-code the scorer name or guardrail list.

# 8. Registry

Create a registry mapping configuration IDs to implementations.

Conceptually:

```ts
getScorer(id);
getReferee(id);
getGuardrails(ids);
getPassageSource(id);
```

Unknown IDs should fail early and clearly.

Do not allow the application to silently fall back to another implementation when configuration is invalid.

# 9. Core pipeline

The pipeline is the central game-engine component.

Implement:

```ts
runCheck(ctx): Promise<CheckOutcome>
```

The pipeline should perform these operations in order:

## Step 1 — local guardrails

Run all local guardrails first.

If a local guardrail fails:

- return `win: false`,
- return the guardrail results,
- do not call the scorer,
- do not consume a Check.

This supports instant local validation and avoids unnecessary API calls.

## Step 2 — scorer

If local guardrails pass:

- invoke the configured scorer,
- record the resulting score/tells,
- consume one Check from the budget.

## Step 3 — remote guardrails

Run configured remote guardrails, passing the `ScoreResult` from Step 2 as the second argument.

A remote guardrail may derive its verdict from `score.raw` or may make its own call. The pipeline must not assume either strategy and must not inspect `raw` itself.

## Step 4 — referee

Only if:

- all required guardrails pass,
- the score is at or below the configured threshold,
- and a referee is configured,

invoke the referee.

## Step 5 — win decision

Win only if:

```text
all active guardrails passed
AND score <= configured threshold
AND referee is absent OR referee approved
```

Return a complete `CheckOutcome`.

Example:

```ts
export type CheckOutcome = {
  guardrails: Array<{
    id: string;
    result: GuardrailResult;
  }>;
  score?: ScoreResult;
  referee?: RefereeResult;
  win: boolean;
};
```

The pipeline should be deterministic with respect to its inputs and module outputs.

# 10. Initial implementations

## 10.1 Mock scorer

Build this first.

Purpose: test the entire framework without an API.

For example:

```ts
const mockScorer: Scorer = {
  id: "mock",

  async score(ctx) {
    return {
      score: someDeterministicFunction(ctx.current),
      tells: [],
    };
  },
};
```

The exact fake scoring function is unimportant.

It should be deterministic so tests are repeatable.

The mock scorer should make it possible to deliberately test:

- winning states,
- losing states,
- changing scores,
- budget exhaustion.

Do not use randomness in the mock scorer.

## 10.2 `not-empty`

A local guardrail.

Pass if the current text contains meaningful non-whitespace characters.

## 10.3 `length-ratio`

A local guardrail.

Calculate:

```text
currentWordCount / originalWordCount
```

and require the ratio to be inside configurable bounds.

Initial default:

```text
0.7 <= ratio <= 1.3
```

This is a simple anti-cheating/validity constraint, not a semantic guarantee.

## 10.4 `none` referee

Always approve.

```ts
const noneReferee: Referee = {
  id: "none",

  async verify() {
    return {
      approved: true,
      reasons: [],
    };
  },
};
```

# 11. Static passage source

For v1, passages are pre-generated or manually entered offline.

Runtime generation is explicitly out of scope.

Example:

```json
[
  {
    "id": "p0001",
    "topic": "sourdough starter",
    "text": "..."
  }
]
```

The passage source loads the bank and provides:

```text
getRandom(excludeId?)
```

Selection is uniformly random over the bank, excluding `excludeId` when the bank has more than one entry. Randomness lives only in the passage source; nothing else in the core is random.

For Milestone 1, the bank may contain three to five hand-written AI-ish passages so the loop can be played. A larger generated bank arrives in Milestone 3b.

# 12. First UI

The first UI should be functional rather than polished.

Required elements:

1. passage editor
2. Check button
3. New passage button
4. checks remaining
5. score display
6. win/loss state
7. basic guardrail feedback
8. optional original-text toggle

The UI must call the core game logic rather than implement scoring rules itself.

## 12.1 UI responsibilities

The UI may:

- display text,
- collect edits,
- display current state,
- display results,
- display remaining budget,
- show feedback,
- request a new passage from core game state.

The UI must not:

- decide what counts as a win,
- choose a scorer,
- directly call Anthropic/OpenAI,
- contain guardrail logic,
- contain score threshold logic,
- pick passages itself.

Those belong in the core/config/provider layers.

## 12.2 New passage button

Pressing **New passage**:

- asks core game state for `passageSource.getRandom(currentPassageId)`,
- resets the editor to the new passage's text,
- resets the Check budget,
- clears the previous score, tells, and win/loss state.

It is always enabled, including mid-puzzle and after a win or loss. If the current puzzle has unsaved edits and at least one Check has been used, the UI may ask for confirmation; this is optional.

---

# 13. Check budget

Default:

```text
6 checks per puzzle
```

Editing itself does not consume a check.

A check is consumed only when the pipeline reaches the scorer.

A failed local guardrail therefore does not consume a check.

A scorer/API failure must not consume a check.

This ensures that a temporary network/API error does not penalize the player.

The budget should be represented in core game state, not only in the UI. Drawing a new passage resets it.

---

# 14. Initial win condition

Use:

```text
score <= 2
AND
all configured guardrails pass
AND
referee is absent OR approved
```

The numeric threshold is intentionally configuration rather than hard-coded game logic.

Example:

```ts
win: {
  scoreAtOrBelow: 2,
}
```

Future testing may change this to 1, 3, or another interpretation without changing the engine.

---

# 15. First real scorer: simple LLM scorer

Only after the framework works with the mock scorer, implement a real scorer.

The first real scorer should be intentionally simple:

```text
one model call
one prompt
structured JSON
0–10 score
optional tells
```

Do not build a sophisticated multi-model system.

The first scorer contract is:

```ts
{
  score: number;
  tells: Tell[];
}
```

Suggested model/provider architecture:

```text
Browser
  |
  | taskId + text
  v
Cloudflare Worker
  |
  v
LLM provider
```

The API key must never be shipped to the browser.

The browser should call a narrow server endpoint such as:

```text
POST /api/task
```

with a known task identifier.

The Worker validates the task identifier and constructs the actual provider request.

Do not expose a generic "arbitrary prompt" endpoint.

A starting prompt, response schema, and parser rules for the first scoring task are given in **Appendix A**. They are starting points to be tuned with the evaluation harness, not fixed requirements.

---

# 16. Provider/task layer

The game should distinguish between:

- **scorer interface**
- **provider/task mechanism**

A scorer knows what game-level result it needs.

The provider knows how to obtain a model response.

Conceptually:

```text
Scorer
   ↓
task client
   ↓
server task registry
   ↓
LLM provider
```

Use task IDs and versions so prompt/rubric changes can be tracked.

Example:

```text
score-v1
generate-v1
```

Future versions may become:

```text
score-v2
score-human-calibrated-v1
```

Do not make the game logic depend on these specific names.

Each task definition (prompt, model, response schema, parser) lives in `packages/shared/src/tasks` and is imported by both the Worker (to build the provider request) and the client or scripts (to parse and type the response). The task's `version` is part of the cache key.

---

# 17. API caching and failure behavior

For the real LLM scorer:

- cache identical task/input combinations,
- rate-limit abusive clients,
- cap maximum input length,
- return structured errors,
- keep secrets server-side.

A cache key should incorporate at least:

```text
task ID
task version
relevant input payload
```

A scorer failure should result in:

```text
no budget consumed
retry available
current game state preserved
```

Do not silently convert an API error into score 0, score 10, or a win/loss.

# 18. Tests required before calling the framework complete

Use Vitest.

At minimum, test:

## Registry

- known scorer ID resolves correctly,
- unknown scorer ID fails clearly,
- known guardrail IDs resolve,
- unknown guardrail IDs fail,
- referee selection works.

## Pipeline ordering

- local guardrail failure prevents scorer call,
- local guardrail failure does not consume budget,
- scorer runs when local checks pass,
- remote guardrails run after scorer and receive the `ScoreResult`,
- referee runs only for a would-be win,
- referee does not run for clearly losing scores.

## Win logic

- score below threshold + guardrails pass + no referee => win,
- score above threshold => not win,
- guardrail failure => not win,
- referee rejection => not win.

## Budget

- successful check consumes one unit,
- API/scorer failure consumes none,
- local guardrail failure consumes none,
- budget exhaustion prevents further checks,
- drawing a new passage resets the budget and clears prior outcome.

## Passage source

- `getRandom` returns a passage from the bank,
- `getRandom(excludeId)` never returns the excluded passage when the bank has more than one entry.

## Parsing

Once a real LLM scorer exists:

- valid response accepted,
- malformed JSON rejected,
- score clamped/validated,
- invalid tell quotes handled safely.

# 19. First milestones

## Milestone 0 — inspect and establish the project

Before making substantial changes:

- inspect the repository,
- identify existing framework/tooling,
- avoid replacing an existing setup without a reason,
- confirm how the app currently builds and runs.

Produce a concise summary of the discovered structure in the development notes, then proceed.

## Milestone 1 — framework without APIs

Implement:

- core types,
- config,
- registry,
- pipeline,
- mock scorer,
- `not-empty`,
- `length-ratio`,
- `none` referee,
- static passage source with a handful of hand-written passages,
- game state (including budget and New passage),
- minimal UI.

Success criterion:

> A complete game can be played end-to-end, including drawing new passages, without making a network request.

## Milestone 2 — tests

Add the pipeline/registry/budget/passage-source tests listed above.

Success criterion:

> The modular framework is covered by deterministic automated tests.

## Milestone 3 — real LLM scorer

Add:

- provider/task abstraction,
- Cloudflare Worker,
- secret handling,
- basic LLM scorer (`llm-basic`) using task `score-v1` (Appendix A),
- structured response parsing,
- error handling,
- cache,
- the `meaning-fluency` remote guardrail (§23), reading `meaning_preserved` and `fluent` from `score.raw`.

Change config from:

```ts
scorer: "mock";
```

to:

```ts
scorer: "llm-basic";
```

without modifying the core pipeline.

Success criterion:

> The exact same game engine runs with either the mock scorer or the real LLM scorer by changing configuration only.

## Milestone 3b — evaluation harness and passage bank

Add:

- `data/human_corpus.json`: roughly 100 human-written paragraphs of 90–130 words (see Appendix A.4 for sourcing rules),
- `scripts/evalHarness.ts`: runs any registered scorer over `data/passages.json` and `data/human_corpus.json`, prints a score histogram for each set, mean and median, and the two separation figures below,
- `scripts/generateBank.ts`: generates candidate passages with task `generate-v1`, scores each with the active scoring task, and keeps those at or above a configurable minimum score (default 8).

The harness runs in Node against the provider directly (key from environment), reusing the shared task definitions; it does not go through the Worker.

Separation figures the harness must print:

```text
% of bank passages scoring >= 8 untouched        (target: >= 95%)
% of human paragraphs scoring >= 6               (target: <= 10%)
```

Tune the `score-v1` prompt until both targets are met, then generate a bank of at least 50 passages.

Success criterion:

> One command reports how any registered scorer separates the AI bank from the human corpus, and the shipped bank was validated by the active scorer.

## Milestone 4 — mobile pass

Verify on:

- desktop Chrome/Safari,
- iPhone Safari,
- Android Chrome if available.

Fix:

- text input behavior,
- viewport sizing,
- button accessibility,
- loading states,
- scrolling,
- touch interactions.

Do not add visual complexity merely for its own sake.

# 20. Future intentions — preserve these extension points

These are explicitly future possibilities. Do not implement them during the framework-first phase unless needed for an interface.

## 20.1 Better scorers

Potential future implementations:

```text
llm-basic
llm-detailed
openai-basic
anthropic-basic
rule-based
commercial-detector
embedding-classifier
human-calibrated-classifier
browser-local-model
ensemble
```

The core game must not care which one is active. Every one of them should be runnable through the evaluation harness with no changes to the harness.

## 20.2 Human-perception calibration

The long-term research goal is to make the score correspond more closely to **human perception of AI-likeness** rather than merely an LLM's judgment.

Existing datasets containing human judgments may be used later.

A promising benchmark is the Russell/Karpinska/Iyyer human-detector dataset, which includes multiple human judgments per article and confidence/explanation information.

Do not build a new human-annotation system in the framework phase.

The architecture should simply permit a future scorer to be evaluated/calibrated against such datasets. The evaluation harness is the natural place for that comparison.

## 20.3 More sophisticated score semantics

The initial `0–10` score is intentionally simple.

Future scorers might return:

```text
continuous score
probability-like score
human-agreement estimate
confidence
uncertainty
multiple sub-scores
```

Do not force the current UI/game engine to expose all of these.

The game-level score should remain an abstraction.

## 20.4 Guardrails

Possible future guardrails:

```text
word-ratio
embedding-similarity
grammatical
topic-preserved
minimum-edit-distance
maximum-edit-distance
```

Guardrails should remain independent modules.

## 20.5 Referees

Possible future referees:

- none
- stricter LLM judge
- second-model judge
- ensemble disagreement resolver
- human-calibrated final validator

A referee is optional.

## 20.6 Passage generation

Runtime passage generation is not part of v1.

`scripts/generateBank.ts` (Milestone 3b) is the offline pipeline:

```text
generate
  ↓
score
  ↓
validate
  ↓
filter
  ↓
store in static bank
```

The generation mechanism remains separate from the runtime passage source.

## 20.7 Puzzle difficulty

Future puzzle metadata may include:

- initial AI score,
- number of plausible edits,
- estimated minimum solution length,
- number of viable solution paths,
- score-landscape difficulty,
- topic/register.

Do not assume that "number of detected tells" is equivalent to difficulty.

Keep the Passage type extensible enough for future metadata.

## 20.8 In-browser inference

A future browser scorer may use a compact ONNX/Transformers.js model.

The architecture must permit:

```text
browser-local scorer
```

without requiring any change to the core scoring interface.

# 21. Important architectural constraints for the in-IDE LLM

When implementing this project:

## Do

- prefer small interfaces,
- prefer dependency inversion,
- keep configuration centralized,
- keep provider/API code outside UI components,
- keep game rules in the core pipeline,
- use deterministic tests,
- use meaningful names,
- keep functions small,
- preserve future replacement points,
- document non-obvious decisions.

## Do not

- hard-code the active scorer into the pipeline,
- hard-code Anthropic/OpenAI calls into React components,
- hard-code the win threshold in UI components,
- make the API endpoint an arbitrary prompt proxy,
- build future ML systems before the framework works,
- introduce a large editor library before needed,
- create unnecessary abstractions that have no current consumer,
- silently swallow scorer/provider errors,
- let the pipeline or UI read `ScoreResult.raw`; only remote guardrails and referees may.

The objective is **modular simplicity**, not maximum abstraction.

# 22. Definition of "framework complete"

The first framework is complete when all of the following are true:

- The game runs locally.
- A random passage can be loaded from the static passage source, and a new one drawn on demand.
- The player can edit it.
- The player can press Check.
- The core pipeline invokes the configured scorer.
- The score determines a provisional win/loss.
- Guardrails can block a win.
- A referee can be disabled through configuration.
- Check budget is enforced by core logic and reset by New passage.
- Changing scorer IDs in configuration changes the implementation used.
- Tests verify the registry, pipeline, budget, passage source, and win behavior.
- No API key is exposed in the browser.
- The application works on a narrow mobile viewport.

# 23. Definition of "v1 gameplay complete"

After the framework is complete:

- Replace the mock scorer with the first LLM scorer.
- Enable the `meaning-fluency` remote guardrail. Without it, a player can win by replacing sentences with unrelated but human-sounding prose of similar length, or with coherent nonsense. The guardrail reads `meaning_preserved` and `fluent` from the scorer's `raw` payload (Appendix A.2) and fails with a player-readable reason ("The judge thinks the meaning changed" / "The judge thinks this isn't fluent English"). A check that fails this guardrail still consumes a Check, since the scorer ran.
- Provide a bank of at least 50 pre-generated AI-ish passages validated by the harness (Milestone 3b).
- Display a simple 0–10 score/meter.
- Optionally display scorer-provided tells.
- Show remaining Checks.
- Show a win screen and a loss state, each with the New passage button prominent.
- Handle API errors without consuming a Check.
- Make the main game flow comfortable on mobile.

Do not expand the feature set until this loop is enjoyable and technically stable.

# 24. Future game-design direction

The long-term desired experience is not simply:

> remove obvious AI buzzwords.

The game should eventually reward the player for making prose feel genuinely more human while preserving the original meaning.

Potential future improvements include:

- more varied AI-ish writing styles,
- subtler AI signatures,
- different genres/registers,
- hidden versus visible feedback,
- score trajectories,
- difficulty based on actual edit paths,
- practice versus challenge modes,
- shareable results,
- player learning over time.

These should be layered on top of the existing framework rather than baked into it.

# Appendix A — Starting points for Milestone 3 and 3b

Everything in this appendix is a **first draft to be tuned with the evaluation harness**. It exists so the agent does not have to invent a rubric from nothing at Milestone 3. Nothing here is required to be implemented before Milestone 3.

## A.1 Task definition shape

Each file in `packages/shared/src/tasks` exports:

```ts
export const task = {
  id: "score-v1",
  version: 1,
  model: "claude-haiku-4-5",          // provider-specific; only the Worker and scripts read this
  buildRequest(payload): ProviderRequest,
  parse(raw: unknown): ParsedResult,   // throws on malformed input
};
```

The Worker rejects any `taskId` not present in the task registry. The client never sends prompt text.

## A.2 `score-v1` — scoring task

Model: Claude Haiku 4.5 (`claude-haiku-4-5`), temperature 0, `max_tokens` ~400, JSON output. Use prompt caching for the system prompt if the provider supports it.

System prompt (draft):

```
You are the judge in a game. Players are given a passage that was written by an AI assistant and edit it until it reads like a human wrote it. Rate how strongly the CURRENT passage still reads as AI-assistant prose to a careful, experienced reader.

Signals of AI-assistant prose include: generic importance-framing openers; "it's not X, it's Y" constructions; lists of exactly three parallel items; frequent em dashes; overused vocabulary (delve, tapestry, testament, pivotal, foster, landscape, robust, navigate, underscore, crucial, seamless, multifaceted, leverage, realm, embark); vague attribution ("experts agree"); false ranges ("from X to Y" with no real spectrum); puffery about significance; uniform sentence rhythm; a closing sentence that restates the opening. Human prose tends to have specific detail, uneven rhythm, idiosyncratic word choice, and no summarizing closer.

Also judge whether the CURRENT passage preserves the meaning of the ORIGINAL, and whether it is fluent, grammatical English. Typos, gibberish, deleted content, or nonsense do not make text "human"; mark fluent=false or meaning_preserved=false instead of lowering the score.

Respond with JSON only:
{
  "score": <integer 0-10; 10 = obviously AI-assistant prose, 0 = unmistakably human>,
  "tells": [ { "label": "<short-kebab-label>", "quote": "<exact short quote from CURRENT passage>" } ],
  "meaning_preserved": <true|false>,
  "fluent": <true|false>
}
List at most 8 tells. Quotes must appear verbatim in the CURRENT passage. If score <= 2, tells may be empty.
```

User message template:

```
ORIGINAL:
{original}

CURRENT:
{current}
```

Parser rules:

- Reject (throw) if the response is not valid JSON or lacks a numeric `score`.
- Clamp `score` to an integer in 0–10.
- Drop any tell whose `quote` is not a case-sensitive substring of `current` after trimming; cap tells at 8; default to `[]` if absent.
- Default `meaning_preserved` and `fluent` to `true` if absent, and log a warning; the `meaning-fluency` guardrail reads them from `ScoreResult.raw`.

The `llm-basic` scorer maps the parsed result to `{ score, tells, raw: parsed }`.

## A.3 `generate-v1` — passage generation task (scripts only)

Model: a Sonnet-class model. Used only by `scripts/generateBank.ts`; never registered as a callable task in the Worker.

System prompt (draft):

```
You write short passages in the most stereotypical "AI assistant" register, for use as game puzzles.
```

User message template:

```
Write one paragraph of 90–130 words about: {topic}
Register: {register}
Make it read as unmistakably AI-generated. Include ALL of the following:
- an opening sentence that frames the topic's importance
- at least one list of exactly three parallel items
- at least one "it's not X, it's Y" (or "not just X but Y") construction
- at least two em dashes
- at least three of these words: delve, tapestry, testament, pivotal, foster, landscape, robust, navigate, underscore, crucial, seamless, multifaceted, leverage, realm, embark
- sentences of roughly uniform length
- a closing sentence that summarizes or restates the opening
No headings, bullets, bold, or emoji. Plain prose only. Return only the paragraph.
```

Vary `{topic}` and `{register}` widely (product blurb, LinkedIn post, recipe intro, history summary, cover letter, product review, travel description, motivational post, event announcement, FAQ answer).

Bank entry format produced by the script:

```json
{
  "id": "p0001",
  "topic": "sourdough starter",
  "register": "recipe intro",
  "text": "...",
  "generatedWith": { "task": "generate-v1", "scoredWith": "score-v1@1", "score": 9 }
}
```

The runtime `Passage` type ignores `generatedWith`; it is provenance for the harness.

## A.4 Human corpus sourcing rules

`data/human_corpus.json` is a list of `{ id, text, source }` entries, 90–130 words each, roughly 100 entries. Use only:

- public-domain prose (Project Gutenberg excerpts),
- CC-BY-SA text with attribution in the `source` field (for example, Wikipedia paragraphs),
- the developer's own writing.

Do not include copyrighted contemporary prose. Aim for a mix of registers comparable to the bank's (informal, explanatory, narrative, persuasive).

# Appendix B — Decisions log

Open questions resolved during implementation. Each entry proposes a default that stands until overridden. Dates are absolute.

## B.1 Milestone numbering (2026-09-29)

The implementation request labelled "Milestone 1" as workspace init + `score-v1` task + Cloudflare Worker, which is the server half of §19 Milestone 3. The mock framework (§19 Milestone 1), its tests (Milestone 2), and the `llm-basic` scorer + `meaning-fluency` guardrail (client half of Milestone 3) follow next, in that order. §19 is unchanged; this log records the mapping.

## B.2 Package layout and naming (2026-09-29)

- pnpm workspace with packages `@unslop/shared`, `@unslop/web`, `@unslop/worker`, `@unslop/scripts`. Scope follows the repository name; the product name "De-AI" appears only in UI text.
- `@unslop/shared` is consumed as TypeScript source (`main` points at `src/index.ts`); no build step. Vite, Vitest, and wrangler all bundle TS directly.
- Vitest runs per package via `pnpm -r test`; ESLint (flat config) and Prettier run at the root.
- Tailwind is deferred until the first UI milestone needs it.

## B.3 Task definition contract (2026-09-29)

`TaskDefinition<Payload, Result>` adds two things to the shape in A.1: `validatePayload(input: unknown): Payload` (the Worker never trusts the client) and a second `parse` argument carrying the validated payload, because the quote-validation rule needs `current`. `buildRequest` returns a provider-neutral `ProviderRequest` (`model`, `system`, `messages`, `maxTokens`, `temperature`, optional `outputSchema`); only the Worker's provider adapter knows the Anthropic SDK.

## B.4 Where parsing happens (2026-09-29)

The Worker parses the model output before caching and returns the typed result. Consequences: malformed model output is never cached, the client receives `{ ok, taskId, version, result, cached }` and does not need the parser at runtime, and Node scripts can still import the same `parse` for the harness. A parse failure is a `502 parse_error` with `retryable: true`, so the scorer surfaces an error and no Check is consumed.

## B.5 `score-v1` request details (2026-09-29)

- Model `claude-haiku-4-5`, temperature 0, `max_tokens` 512 (A.2 says ~400; 512 leaves room for eight quoted tells without truncation).
- Structured output via `output_config.format` with the JSON Schema exported from the task, so responses are schema-valid JSON. The parser still enforces the A.2 rules (clamp, quote validation, cap of 8, defaults with warnings) because the schema cannot express numeric ranges or array limits.
- A `stop_reason` of `max_tokens` or `refusal` is reported as a provider error rather than parsed.
- Prompt caching is not enabled: the Haiku 4.5 cacheable minimum is 4096 tokens and the system prompt is roughly 400. Revisit if the prompt grows or the model changes.
- `parse` returns `warnings: string[]` (empty on a clean response) rather than logging directly; the Worker logs them. This keeps the parser pure and testable.
- Payload limit: 4000 characters per field (`SCORE_V1_MAX_CHARS`). Bank passages are 90–130 words.

## B.6 Worker behaviour (2026-09-29)

- Route: `POST /api/task` only, plus `GET /api/health`. Unknown paths return 404 JSON. No CORS handling: in development Vite proxies `/api` to the Worker on port 8787; in production the Worker will serve the built SPA from the same origin (assets binding added when the UI exists).
- Cache: KV namespace `TASK_CACHE`, key `task:<id>@<version>:<sha256(canonical payload)>`, TTL 30 days (`CACHE_TTL_SECONDS`). Only successfully parsed results are stored.
- Rate limit: KV namespace `RATE_LIMIT`, fixed window of 60 s per client IP (`CF-Connecting-IP`), default 30 requests (`RATE_LIMIT_PER_MINUTE`). KV is eventually consistent, so this is a best-effort brake; the limiter sits behind a small interface and can be swapped for Cloudflare's rate-limit binding later.
- Errors are `{ ok: false, error: { code, message, retryable } }` with codes `bad_request`, `invalid_payload`, `unknown_task`, `rate_limited`, `provider_error`, `parse_error`, `server_misconfigured`.
- Secrets: `ANTHROPIC_API_KEY` from `.dev.vars` locally (git-ignored; `.dev.vars.example` is committed) and `wrangler secret put` in production. A missing key returns `500 server_misconfigured` instead of reaching the provider.
- Request bodies over 64 KB are rejected before parsing.

## B.7 Milestone 1 framework decisions (2026-09-29)

- `CheckOutcome` gains `checkConsumed: boolean`. The pipeline stays pure and never touches the budget; it reports whether the scorer ran, and game state spends the Check. Scorer errors propagate out of `runCheck`, so a failed call can never be mistaken for a consumed check.
- `GameConfig.referee` is optional. Undefined means no referee; `"none"` (the default) keeps the referee slot exercised with an always-approve implementation.
- `core/registry.ts` is a generic factory-based registry with no knowledge of implementations; the built-ins are listed in `config/registry.ts` next to the game config. Guardrail factories receive `guardrailParams[id]`, so `length-ratio` reads its bounds from config. Unknown ids throw an `UnknownIdError` naming the known ids.
- Mock scorer: two points per occurrence of a small marker set (em dash, "it's not just X", "in today's … world", stock words, vague authority, summary closers), capped at 10, with each hit reported as a tell. Deterministic, and playable offline because deleting markers lowers the score.
- Passage bank lives at `data/passages.json` (five hand-written passages) and is imported at build time through Vite's JSON import; `validateBank` rejects missing ids, duplicates, and empty text at startup. Randomness is confined to `createStaticBank`, which takes an injectable `random` for tests.
- Game state is a small framework-free store (`getState`/`subscribe`/actions) with phases `loading | playing | checking | won | lost`; React binds to it with `useSyncExternalStore`. A scorer failure sets `error`, leaves the budget untouched, and returns to `playing`. Editing is disabled after a win or loss until New passage.
- Tailwind v4 via `@tailwindcss/vite` with no config file. Layout is a single column with a fixed bottom action bar padded for the iOS safe area.
- Original-text toggle is a native `<details>` element. The optional New-passage confirmation from §12.2 is not implemented.

## B.8 Hosting (2026-09-29)

- Source lives on GitHub. The web app is served by GitHub Pages at the custom domain `unslop.app`, so Vite's `base` stays `/`. The `CNAME` file and the Pages deploy workflow (build `apps/web`, publish `dist`) are added when the first deploy happens.
- The Worker is hosted on Cloudflare, which is the only place the API key exists. This supersedes the same-origin assumption in B.6: the Worker gains CORS restricted to `https://unslop.app` (plus localhost in dev), and the client reads its API base URL from `VITE_API_BASE_URL` at build time, defaulting to `/api` so the local Vite proxy keeps working. Both changes land in Milestone 3, when the client first calls the API.
- Milestone 1 and 2 builds are fully static and need no Worker to run on Pages.

## B.9 Milestone 3 decisions (2026-09-29)

- `mock` stays the default scorer until Milestone 3b delivers a harness-validated bank; `llm-basic` and `meaning-fluency` are registered and opt-in via `game.config.ts`.
- `providers/taskClient.ts` is the browser's only route to a model. It reads `VITE_API_BASE_URL` at build time (default `/api`, which the Vite proxy forwards to the local Worker) and converts the Worker's structured errors into `TaskClientError { code, retryable }`. Network and non-JSON failures are marked retryable.
- `llm-basic` maps one `score-v1` result onto `{ score, tells, raw }`; the whole task result is the `raw` payload. Client errors propagate unchanged so game state reports them and spends no Check (spec §17).
- `meaning-fluency` fails only on an explicit `false`. A raw payload missing either field passes, so a future scorer that lacks those fields does not block every win.
- Worker CORS: `ALLOWED_ORIGINS` var (comma-separated) in `wrangler.toml`, defaulting to `https://unslop.app,http://localhost:5173`. Preflights answer 204; unlisted origins get no CORS headers rather than an error.

## B.10 Milestone 3b decisions (2026-09-29)

- The Anthropic adapter moved from the Worker into `packages/shared/src/providers` and is exposed as the `@unslop/shared/anthropic` subpath, so the Worker and the Node scripts share one provider implementation. The `Provider` interface and `ProviderError` are exported from the package root; the SDK-backed adapter is not, so the web bundle never pulls in the SDK.
- `ProviderRequest.temperature` is optional. `score-v1` still pins 0; `generate-v1` omits it because Claude Sonnet 5.5 rejects non-default sampling parameters. `generate-v1` uses `claude-sonnet-5-5` with `max_tokens` 2048 to leave room for adaptive thinking, and is exported from the shared package but never registered in `callableTasks`.
- Scripts keep a disk cache of parsed results under `scripts/.cache/results` (git-ignored) keyed exactly like the Worker's KV cache, so reruns while tuning are free until a task version is bumped. Raw Gutenberg and Wikipedia downloads are cached under `scripts/.cache/raw`.
- `data/human_corpus.json` was built by `scripts/buildHumanCorpus.ts` on 2026-09-29: 5 paragraphs from each of 12 Gutenberg books (narrative, informal, explanatory, persuasive) plus the first in-range paragraph from 35 Wikipedia articles on everyday topics, 95 entries total. Selection is deterministic; each entry carries `source` and `register`. The builder sends a generic User-Agent with no personal contact details.
- First harness run with the untouched Appendix A.2 prompt met both targets (bank ≥8: 100%, human ≥6: 2.1%), so `score-v1` stays at version 1 with no tuning.
- `scripts/generateBank.ts` pairs 60 topics with the ten A.3 registers deterministically, rejects candidates outside 80–140 words or flagged by the judge as non-fluent, and writes provenance per entry. The first run kept 60 of 60 candidates. The five hand-written passages were replaced; the runtime `Passage` type ignores the extra `register` and `generatedWith` fields.
- `game.config.ts` now defaults to `llm-basic` with `meaning-fluency` enabled, which completes the spec §23 checklist except for the mobile pass. Local development therefore needs `pnpm dev:worker` running; switching back to `mock` is a one-line config change.

## B.11 Milestone 4 and deployment decisions (2026-09-29)

No horizontal overflow. Real-device Safari and Android Chrome checks remain for the maintainer.

## B.12 API base URL is an origin (2026-09-29)

The first production deploy failed because `VITE_API_BASE_URL` was set to the Worker origin while the client expected origin plus `/api`. The client now treats the variable as an origin only and always posts to `<origin>/api/task`, stripping a trailing slash or a trailing `/api` if present. Empty means same origin, which the Vite proxy serves in development. This supersedes the base-URL wording in B.8 and B.9.
